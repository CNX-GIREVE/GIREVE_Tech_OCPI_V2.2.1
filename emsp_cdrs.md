# `Cdrs Module Specifications`

IOP follows the OCPI standard for Sessions sent by a CPO. [See OCPI 2.2.1 specifications.](https://github.com/ocpi/ocpi/blob/release-2.2.1-bugfixes/mod_cdrs.asciidoc)

## CDR: Object IDs

The id field of the CDR object is mapped with the id provided by the CPO platform.

The location_id, EVSE_uid, and connector_id fields within the CDR object are mapped to the IDs provided by the CPO platform. 

The uniqueness of these IDs is guaranteed by the combination of the country_code and party_id of the CPO in the body of the request.

The session_id field of the CDR object corresponds to the ID generated by Gireve and not the ID from the CPO platform as done in the session module. 


## CDR content
The “total_time” value is the total duration of this session (including the duration of charging and not charging). 
It doesn’t include the duration during which the EVSE is out of order so cannot supply the service. The out of order duration should be free of charge for eMSPs.

## Add billing information in “Remark” field

In some cases, the CPO is not able to send a consistent B2B price in the CDR. (“total_cost” not mandatory for CPOs connected through eMIP protocol, CPO not able to calculate the price, …)

For these reasons GIREVE has implemented a billing feature, included in its “Clearing” service, which calculates the B2B price for a given CDR and injects this information in the CDR.
IOP uses the “Remark” field in CDRs sent to the eMSP to send extra information about this billing. 

The “Remark” field is prefixed by :
-  [*] prefix: The total_cost provided in the CDR is calculated by Gireve.
-  [?] prefix: The total_cost provided in the CDR is not significant. The B2B price has not been sent by the CPO and/or the eMSP has not subscribed to Gireve Clearing service.
-  No prefix: The total_cost provided in the CDR has been sent by the CPO.  

## Fields Not Implemented by Gireve

**<ins>CreditCDR</ins>**
For the moment, the “credit” field is not implemented by Gireve; therefore, eMSPs will not receive it.

We recommend that the CPO transmit PATCH Sessions that Gireve will not consider at first, but that Gireve will consider at some point.
-  CPO send CDR: Gireve records and sends to eMSP.
-  CPO send CreditCDR: Gireve don’t take in consideration.
-  CPO send new CDR: Gireve records and sends to eMSP.

**<ins>Credit_reference_id</ins>**
The “credit_reference_id” field is not implemented by Gireve; therefore, eMSPs will not receive it.

**<ins>Home_charging_compensation</ins>**
The “home_charging_compensation” field is not implemented by Gireve; therefore, eMSPs will not receive it.


## PULL CDRs ToIOP: Get List Pagination

Pull CDRs ToIOP is not currently implemented.

### Information and Requirements

-  Unlike Session IDs and authorization references, which are replaced with Gireve IDs, IOP forwards CDRs with CPO IDs to eMSPs. The same applies to Locations and Tariffs.
-  IOP uses the “Remark” field in CDRs sent to the eMSP to send extra information about this billing.
-  The fields “credit”, “credit_reference_id” and “home_charging_compensation” are not implemented by Gireve, therefore, the eMSP will not receive it.
